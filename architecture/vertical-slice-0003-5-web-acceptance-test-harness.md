# Vertical Slice 0003.5: Web Acceptance Test Harness

## Purpose

Prove that HiveSight has a repeatable browser-level acceptance test harness for the Web UI, so user-facing vertical slices can be checked through the same path a Beekeeper uses in the browser.

This is a testing-enablement slice rather than a new product feature. It closes the gap between API-level BDD coverage and the actual browser workflow by making the Slice 3 evidence-review path executable through Playwright from the VS Code command line and, later, CI.

This slice also introduces a lightweight slice verification report: one developer command runs the current test set and writes a coherent human-readable report showing what was run, what passed or failed, and where browser failure artifacts can be found. The report describes executed checks; it does not claim formal code coverage percentages.

Slice 3.5 started with plain Playwright tests so the team could first stabilize the browser harness itself. Later Slice 0013 planning parked UI-level Gherkin as a future option rather than a near-term requirement; until deliberately reselected, UI acceptance coverage uses Playwright specs plus generated slice verification reports.

## End-To-End Behaviour

The developer runs one command from the repo or Web App package. That command starts the Core API and Web UI automatically, then executes Playwright browser acceptance tests against the Web UI. The Web package owns the implementation command, and the repo root exposes a convenience command so the developer does not need to remember package internals.

The first browser acceptance test covers the happy path for the current product slice: the test opens the Web UI, accepts the Workspace Data Use Agreement, creates an Apiary, creates a Hive, creates an Inspection, uploads a fixture image as an Inspection Photo, processes the deterministic stub Analysis Run, and verifies the evidence panel.

The test asserts browser-observable behaviour, not internal implementation details. It checks that the Core API is reachable from the UI, that the upload and processing workflow completes, that the evidence view displays the original image, that complete and partial visible bee overlays are present, and that the UI keeps the deterministic-stub caveat visible. It also performs practical overlay alignment checks: the image container has non-zero dimensions, each annotation box is visible inside the image bounds, and the boxes remain inside the image bounds after switching to a narrower viewport. Pixel-perfect screenshot baselines are not part of this slice.

The harness uses stable UI test hooks where role/name selectors would be too fragile. These hooks should be intentional and sparse: they support acceptance testing without turning the UI into a test-only surface.

The test command should be usable by the developer in VS Code and should be suitable for later CI adoption. Tests run headlessly by default, with a headed/debug command available for local diagnosis. Failure artifacts should be retained only when a test fails.

If stable test isolation needs more than automatic service startup, the implementation may add a dev/test-only reset seam. Any reset capability must be unavailable in production and limited to acceptance-test setup.

The slice also adds a repo-level verification command that runs the available checks for the current slice and writes a markdown report. At minimum, the report records the command run, pass/fail status, and useful summary output for Core API tests, Analysis Service tests, Web TypeScript checking, and Web browser acceptance tests. The report should make API-level BDD results visible as part of the Core API test output and should point to Playwright trace/screenshot/video locations when browser acceptance tests fail.

## Layers Touched

- Web UI: Adds Playwright test dependency/configuration, stable test hooks for the Slice 3 workflow, a committed test fixture image, headless and headed acceptance commands, and browser acceptance tests. The UI behaviour itself should not change except for test-friendly attributes.
- Core API: Not touched unless a small dev-server command, CORS default, or test reset endpoint is required. Any reset capability must be dev/test-only and unavailable as a production feature.
- Analysis Service: Not touched. Slice 3 still uses the deterministic stub behaviour already exposed through the Core API.
- Storage: Uses the existing local/dev object storage path through the Core API.
- Queue or async boundary: Uses the existing dev/demo process action from Slice 2.
- Contracts: No product API contract change is expected. Test commands, local environment variables, and the slice verification report format become the new operational contract.
- Observability: Playwright reports, traces, screenshots, optional video on failure, and browser console errors are captured as test evidence where practical. Passing runs should remain quiet.
- Verification reporting: Adds a repo-level command that runs the current verification suite and writes a markdown report, for example under `reports/slice-verification/latest.md`.

## Test Seams

- Seam: Web UI browser workflow
- Behaviour verified: a Beekeeper can complete the Slice 3 workflow from the browser and see annotation evidence.
- Test style: Playwright end-to-end browser test.

- Seam: Web UI to Core API integration
- Behaviour verified: the Web UI can reach the Core API, send dev-authenticated requests, upload the fixture image, process analysis, fetch evidence, and load protected photo bytes.
- Test style: Playwright test against local Vite and local Core API.

- Seam: Evidence rendering
- Behaviour verified: original photo is visible; complete visible bee and partial visible bee overlays render, sit inside the image bounds, and remain inside bounds after a responsive viewport change.
- Test style: Playwright assertions using stable test hooks, bounding boxes, and failure-only artifacts. Pixel-perfect screenshot approval is not required in this slice.

- Seam: Local developer command
- Behaviour verified: a developer can run the browser acceptance suite from VS Code without hand-building hidden setup; the command starts both local services.
- Test style: package script, root convenience script, and documented command.

- Seam: Slice verification report
- Behaviour verified: a developer can run one verification command and receive a coherent summary of Core API tests, Analysis Service tests, Web TypeScript check, and Web browser acceptance tests.
- Test style: script-level smoke test or documented manual check for the generated markdown report.

## Data Shape

Minimum test/support data:

- Fixture Inspection Photo: small deterministic image file committed under the Web App test fixture area.
- Test user: the existing dev User id used by the Web UI.
- Test selectors: stable, sparse `data-testid` values for major workflow controls and evidence elements.
- Playwright configuration: base Web UI URL, Core API URL, Chromium browser project, headless default, headed/debug mode, failure-only trace/screenshot behaviour, and web-server startup commands for both Core API and Web UI.
- Slice verification report: generated markdown file with timestamp, overall result, per-check command, per-check status, concise output summary, and failure artifact locations where available.

Candidate command shape:

- `pnpm --filter @hive-sight/web test:acceptance`
- `pnpm --filter @hive-sight/web test:acceptance:live-api`
- `pnpm --filter @hive-sight/web test:acceptance:headed`
- `pnpm test:acceptance:web`
- `pnpm test:acceptance:web:live-api`
- `pnpm verify:slice`
- Stub Core API startup command managed by Playwright config: `cd services/core-api && ./.venv/bin/python -m uvicorn hive_sight_core_api.main:app --host 127.0.0.1 --port 8020`
- Stub Web UI startup command managed by Playwright config: `pnpm --filter @hive-sight/web dev --host 127.0.0.1 --port 5193`
- Stub Web UI base URL default: `http://127.0.0.1:5193`
- Stub Core API base URL default: `http://127.0.0.1:8020`
- Live-API acceptance profile: Core API `8030`, Web UI `5203`, Postgres dev database.
- Report output default: `reports/slice-verification/latest.md`

## Out Of Scope

- New beekeeper-facing product behaviour beyond any stable test hooks needed for automation.
- Real authentication, production auth provider integration, or browser login flows.
- Real object storage, signed upload URLs, or signed view URLs.
- Real queue infrastructure or worker orchestration.
- Real bee detection or Varroa detection.
- Admin/reviewer workflow testing.
- Full visual regression testing or screenshot approval baselines.
- Cross-browser matrix testing beyond one reliable local browser.
- Mobile-device farm testing. A single responsive viewport check is enough for this slice.
- Error-path browser tests such as missing terms, invalid file type, cross-Workspace evidence access, or failed analysis.
- UI-level Gherkin step definitions. Later Slice 0013 planning parked this as a future option rather than a near-term requirement.
- CI pipeline integration if local execution is not yet stable; CI can be a follow-on step.
- Formal code coverage thresholds or coverage percentage claims.
- A historical report dashboard, trend analysis, flaky-test tracking, or quality gate service.
- Replacing detailed test runner output; the report summarizes and links or points to artifacts rather than duplicating every line.
